# 团长内容增长 Agent 首版单机生产部署与数据保护手册

> 文档日期：2026-08-27
> 适用架构：一台 Ubuntu 服务器、一个 Next.js Node.js 进程、一个 SQLite 主库、Nginx HTTPS 入口
> 首版原则：不使用 Docker、PM2、Redis、消息队列或多实例负载均衡；始终只有一个应用进程写生产 SQLite。

## 一、目录和账号约定

```text
/opt/content-agent/
  current -> /opt/content-agent/releases/<版本号>
  releases/<版本号>/
/var/lib/content-agent/production.sqlite
/var/backups/content-agent/
/var/log/content-agent/
/etc/content-agent/content-agent.env
/etc/systemd/system/content-agent.service
/etc/systemd/system/content-agent-backup.service
/etc/systemd/system/content-agent-backup.timer
/etc/nginx/sites-available/content-agent.conf
```

应用进程使用独立系统账号 `content-agent`。代码目录只读，数据库目录和备份目录分别授权，不把数据库、环境文件或备份放入 Git 仓库。

建议最低配置为 4 核 CPU、8 GB 内存、80 GB SSD。首版 systemd 将单进程内存上限设为 3 GB；磁盘可用空间默认低于 1024 MB 时，就绪检查失败。该配置服务的是单实例内容闭环，不代表可以同时执行大量模型任务；模型并发由全局、租户和平台三层额度共同限制。租户之间按 `tenant_id` 隔离，平台爆款拆解使用独立平台作用域，避免内部运营任务占满某个团长额度。

## 二、服务器初始化

以下操作在 Ubuntu 22.04/24.04 上由有 sudo 权限的运维人员执行：

```bash
sudo useradd --system --home /opt/content-agent --shell /usr/sbin/nologin content-agent
sudo install -d -o content-agent -g content-agent -m 0750 /opt/content-agent/releases
sudo install -d -o content-agent -g content-agent -m 0750 /var/lib/content-agent
sudo install -d -o content-agent -g content-agent -m 0750 /var/backups/content-agent
sudo install -d -o content-agent -g content-agent -m 0750 /var/cache/content-agent
sudo install -d -o root -g adm -m 0750 /var/log/content-agent
sudo install -d -o root -g content-agent -m 0750 /etc/content-agent
```

安装 Node.js 20 LTS 或更高兼容版本、npm、Nginx、rsync、curl 和 logrotate。执行 `node --version`、`npm --version`、`nginx -v`、`logrotate --version` 确认命令可用。不要使用 nvm 为 systemd 提供 Node.js；服务文件默认使用 `/usr/bin/npm`。

## 三、生产环境文件

环境变量的唯一完整定义是当前 release 根目录的 `.env.example`。创建 `/etc/content-agent/content-agent.env` 时以该文件为基线逐项填写，并把权限设为 `0640 root:content-agent`；不要从本文复制一份可能过期的变量列表。

上线复核至少确认：`APP_ENV`/`NODE_ENV` 为生产、`ALLOW_LIVE_MODEL=true`、模型三项配置完整、`PROTOTYPE_DB_PATH=/var/lib/content-agent/production.sqlite`，并关闭原型 API、Demo、Fixture、模拟和清理开关。数据库路径必须是绝对路径，且不能包含 `dev`、`test`、`e2e` 或 `development` 等测试标识。密钥不得写入仓库、命令历史、部署日志或健康接口；实际强校验规则以 `src/lib/runtime-environment-validation.ts` 为准。

首版建议从 `.env.example` 的默认模型保护值起步：全局并行任务 10、单租户并行任务 2、平台运营并行任务 2；单租户每日 500 个任务/500 万 Token，平台每日 200 个任务/300 万 Token，单任务总超时 120 秒。这里限制的是外部模型调用，不是网页在线人数；1 万个已登录团长并不等于 1 万个同时生成任务。上线后应根据 `model_tasks` 的实际峰值、超时率和 Token 成本调整，不能只提高 Nginx 超时而取消应用层并发保护。

## 四、首次部署

把代码拉取到服务器的只读交付目录，例如 `/srv/content-agent-source`。首次部署先注册 systemd unit，但暂不启用 backup timer：

```bash
cd /srv/content-agent-source
sudo cp deploy/systemd/content-agent.service /etc/systemd/system/
sudo cp deploy/systemd/content-agent-backup.service /etc/systemd/system/
sudo cp deploy/systemd/content-agent-backup.timer /etc/systemd/system/
sudo systemctl daemon-reload
```

然后执行：

```bash
cd /srv/content-agent-source
sudo SOURCE_DIRECTORY=/srv/content-agent-source bash deploy/scripts/deploy.sh
```

部署脚本执行以下步骤：

1. 创建不可变 release 目录；
2. 排除 `.env.local`、数据库、测试产物和 Git 元数据；
3. 执行 `npm ci`、类型检查、单元测试和生产构建；
4. 原子切换 `/opt/content-agent/current`；
5. 重启唯一的 systemd 服务；
6. 验证存活、就绪、登录页和健康响应脱敏。

已有版本再次部署时，脚本在构建和切换前强制执行在线备份，必须显式提供生产库和备份目录：

```bash
sudo SOURCE_DIRECTORY=/srv/content-agent-source \
  PRODUCTION_DATABASE=/var/lib/content-agent/production.sqlite \
  PREDEPLOY_BACKUP_DIRECTORY=/var/backups/content-agent \
  bash deploy/scripts/deploy.sh
```

Windows 运维机可以使用：

```powershell
.\deploy\scripts\deploy.ps1 `
  -Server 服务器地址 `
  -User ubuntu `
  -RemoteSourceDirectory /srv/content-agent-source `
  -IdentityFile C:\安全目录\部署私钥
```

脚本不接受或保存 SSH 密码；优先使用受控 SSH Key。旧 release 不自动删除，也不自动回滚。需要回退时由运维人员确认数据库 Migration 兼容性，再把 `current` 指向已验证的旧 release 并重启服务。

## 五、首次正式账号初始化

首次部署的空生产库需要执行一次 `npm run init:production`。初始化密码只放入临时的 root 可读环境文件，执行完成后立即移除；不要长期保留 `INIT_*_PASSWORD`。

```bash
cd /opt/content-agent/current
set -a
. /etc/content-agent/content-agent.env
. /etc/content-agent/initialization.env
set +a
npm run init:production
sudo systemctl restart content-agent.service
```

初始化脚本发现 Demo 数据、已有正式用户或重复初始化时会拒绝覆盖。完成后删除 `/etc/content-agent/initialization.env`，再验证正式平台管理员与租户 Owner 登录。

## 六、systemd 安装

```bash
sudo cp deploy/systemd/content-agent.service /etc/systemd/system/
sudo cp deploy/systemd/content-agent-backup.service /etc/systemd/system/
sudo cp deploy/systemd/content-agent-backup.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now content-agent.service
sudo systemctl enable --now content-agent-backup.timer
```

应用仅监听 `127.0.0.1:3000`。`Restart=on-failure` 在异常退出后 5 秒重启；`SIGTERM` 最多等待 30 秒完成在途请求。不得再启动第二个 `next start`、PM2 cluster 或另一套同库服务。

常用检查：

```bash
systemctl status content-agent.service
systemctl status content-agent-backup.timer
journalctl -u content-agent.service -n 200 --no-pager  # 查看启动、停止和重启等服务生命周期
tail -f /var/log/content-agent/app-access.jsonl
tail -f /var/log/content-agent/app-error.jsonl
ss -lntp | grep 3000
```

## 七、Nginx 与 HTTPS

先把 `deploy/nginx/content-agent.conf` 中的 `example.com` 和证书路径替换为正式域名，再执行：

```bash
sudo cp deploy/nginx/content-agent.conf /etc/nginx/sites-available/content-agent.conf
sudo ln -s /etc/nginx/sites-available/content-agent.conf /etc/nginx/sites-enabled/content-agent.conf
sudo nginx -t
sudo systemctl reload nginx
```

配置包含：

- HTTP 强制跳转 HTTPS；
- TLS 1.2/1.3 和 HSTS；
- 登录接口限速；
- 最大 10 MB 上传；
- 180 秒上游读取超时，覆盖首版 120 秒模型任务总预算；
- 禁止代理缓冲，保留 App Router 流式响应；
- `X-Forwarded-Proto=https`，配合生产 Session Cookie 的 `Secure` 属性。

正式验收必须使用域名和有效证书，不能用服务器 IP 替代 HTTPS Cookie 验收。

## 八、健康检查与告警

```text
GET /api/health/live
GET /api/health/ready
```

`live` 只说明 Node.js 进程存活，不访问数据库或模型。`ready` 检查：

1. 环境安全开关与正式模型配置；
2. SQLite 是否能取得写事务锁；
3. Migration 是否达到代码要求的最新版本；
4. 数据库所在磁盘是否高于最低余量；
5. 最近模型任务状态和连续失败次数。

模型失败不会让应用退出。连续失败达到阈值时，模型状态为 `degraded`，就绪仍可为 200，同时异常日志产生结构化告警。1～2 次连续失败标记为 `warning`。健康响应不会返回数据库路径、模型密钥、Session、邮箱或业务正文。

监控系统建议每分钟请求 `ready`，并采集以下结构化事件：

```text
readiness_configuration_failed
readiness_database_write_failed
readiness_migration_incomplete
readiness_disk_low
model_consecutive_failures
```

告警按事件在单进程内 5 分钟去重，避免健康探针造成日志风暴。

### 请求日志、保存时长与清理

生产日志统一存放在 `/var/log/content-agent/`：

| 文件 | 内容 | 保留时间 |
|---|---|---:|
| `app-access.jsonl` | 应用成功请求、可预期 4xx、模型成功事件 | 最长 14 天 |
| `nginx-access.jsonl` | Nginx 非 5xx 入口请求 | 最长 14 天 |
| `app-error.jsonl` | 应用 5xx、未处理异常、模型失败和运行告警 | 最长 90 天 |
| `nginx-exception.jsonl` | Nginx 5xx 请求 | 最长 90 天 |
| `nginx-error.log` | 反向代理连接、证书和上游错误 | 最长 90 天 |

日志由系统自带 `logrotate.timer` 每日检查。正常日志按天轮转、压缩并最长保存 14 天；异常日志按天轮转、压缩并最长保存 90 天。任一单文件达到 100 MB 时提前轮转，此时可能少于对应天数，以防正常请求或异常风暴耗尽磁盘。安装策略位于 `deploy/logrotate/content-agent`，部署脚本会安装并启用 `logrotate.timer`。

每个 API 响应包含 `X-Request-Id`。Nginx、应用请求日志、模型调用日志和 `model_tasks.request_id` 使用同一编号。根据前端错误编号定位：

```bash
grep 'req_具体编号' /var/log/content-agent/*.log /var/log/content-agent/*.jsonl
systemctl status logrotate.timer
sudo logrotate --debug /etc/logrotate.d/content-agent
```

日志不记录 URL 查询参数、请求体、Session Cookie、Authorization、API Key、完整 Prompt、上传文件或口播稿正文。`audit_logs` 和 `model_tasks` 属于业务审计与任务血缘，不执行 14 天普通日志清理，随数据库备份策略保存。

## 九、在线备份与保留策略

禁止用 `cp production.sqlite` 复制运行中的主文件，也不能忽略 `-wal`、`-shm` 文件。备份脚本调用 SQLite Online Backup API，并在完成后执行：

- `PRAGMA integrity_check`；
- SHA-256 文件校验；
- Migration 版本记录；
- 用户、IP、账号、Run、定稿、发布、指标、复盘、记忆和模型任务等关键表行数清单。

手工执行：

```bash
sudo -u content-agent bash /opt/content-agent/current/deploy/scripts/backup-sqlite.sh \
  /var/lib/content-agent/production.sqlite \
  /var/backups/content-agent
```

默认保留最近 7 个每日备份；每周日额外形成周备份，保留 4 个。systemd timer 每天北京时间 03:15 执行，服务器错过时间后由 `Persistent=true` 补跑。

## 十、隔离恢复演练

恢复脚本必须同时给出备份文件、全新的隔离目录和当前生产数据库路径：

```bash
sudo -u content-agent bash /opt/content-agent/current/deploy/scripts/restore-sqlite.sh \
  /var/backups/content-agent/daily-YYYYMMDD-HHMMSS.sqlite \
  /var/lib/content-agent/restore-drill/2026-08-27 \
  /var/lib/content-agent/production.sqlite
```

脚本具备以下硬保护：

- 目标必须是绝对路径；
- 禁止目标目录等于生产数据库目录；
- 目标目录必须不存在或为空；
- 禁止目标文件等于生产数据库；
- 恢复前验证备份清单，恢复后再次执行完整性检查；
- 恢复前后关键表行数必须一致。

恢复演练只证明备份可恢复，不会切换生产库。真正的生产恢复必须另开维护窗口：停止服务、保留故障库和 WAL、在另一个文件完成验证，再由负责人批准切换；首版脚本不提供直接覆盖生产库命令。

## 十一、上线验收清单

- `npm run typecheck`、`npm test`、`npm run build` 通过；
- `/api/health/live` 为 200；
- `/api/health/ready` 为 200，Migration 版本正确；
- systemd 异常退出拉起测试通过，端口始终只有一个进程；
- Nginx HTTPS、Secure Cookie、安全头、登录限速和 10 MB 上传通过；
- 真实模型最小链路“选题 + 单篇稿”通过；
- 在线备份、manifest、完整性检查通过；
- 隔离恢复后的关键表行数一致；
- journald 能看到磁盘、数据库和连续模型失败的脱敏事件；
- 部署版本、Git 提交、Migration、备份位置和人工回退目标已记录。
