# 团长口播稿 PDCA 交付问题修复实施计划

> 日期：2026-08-24
> 依据：《团长口播稿 PDCA 交付审计》
> 目标：在不扩大首版基础设施和产品范围的前提下，消除生产阻断问题，补齐可感知、可追溯的 PDCA 闭环。

## 实施状态

2026-08-24 已完成本计划第一至第四批代码实施：环境硬隔离、IP 建档上下文一致性、复盘记忆持久化、复盘一键生成下一轮、Run 血缘迁移、旧表层清理和复盘信息层级优化均已落地。

验证结果：70 个单元测试文件、340 项测试通过；TypeScript 检查通过；生产构建通过；15 项 Playwright E2E 通过。生产模式旧调试接口实测返回 404，且请求前后未创建数据库文件。

## 一、修复结论

当前系统已经具备 P（画像与选题）、D（口播稿编辑、定稿、下载和发布登记）、C（真实数据导入、匹配与复盘）、A（确认私有记忆并参与后续创作）的主要能力，但还不能直接按“生产可交付”验收。

修复按以下顺序推进：

1. **先关闭未鉴权旧 API，解除生产安全阻断。**
2. **再修复 IP 建档后的上下文状态不一致。**
3. **把“确认复盘记忆 → 生成下一条”做成用户可见、可追溯的闭环。**
4. **最后清理旧原型双轨代码，并降低复盘页的信息密度。**

首版继续采用现有 Next.js + SQLite 单机架构，不新增微服务、消息队列、Redis、平台数据 API 或产品侧内容质量门禁。

## 二、问题与修复优先级

| 优先级 | 问题 | 影响 | 修复结果 |
| --- | --- | --- | --- |
| P0 | `/api/prototype/*` 未与生产环境硬隔离 | 未授权模型费用、数据越权、生产攻击面 | 本地和 CI 保留受控调试能力；共享测试默认关闭匿名入口；生产固定返回 404 |
| P1 | 新 IP 确认后顶部仍显示“尚未建立 IP” | 用户无法判断建档是否成功，后续上下文容易误解 | 确认成功后完整加载新上下文，顶部、正文和当前账号一致 |
| P1 | 私有记忆确认状态只保存在前端 | 刷新后状态丢失、版本显示错误、失败无提示 | 状态来自数据库，显示真实记忆版本，重复确认幂等，错误可恢复 |
| P1 | 复盘后缺少“生成下一条”的直接动作 | A 到下一轮 P 依赖用户自行跳转，闭环不可感知 | 复盘页一键创建下一轮，并记录来源复盘和记忆版本 |
| P1 | 新旧原型链路同时保留 | 维护成本高，容易误调用旧模拟链路 | 删除无引用入口和组件，保留正式链路依赖的核心服务 |
| P2 | 复盘页内容过长、异常项不突出 | 数据量增加后可读性下降 | 结论优先、异常优先，成功明细默认折叠 |
| P2 | 形成长期记忆的样本阈值不透明 | 用户不理解为何不能确认记忆 | 明确显示当前样本数、门槛和还差几条 |

## 三、目标业务闭环

```mermaid
flowchart LR
  A["选择当前 IP / 内容账号"] --> B["生成今日选题与口播稿"]
  B --> C["分段编辑、定稿、下载"]
  C --> D["登记发布作品"]
  D --> E["导入平台真实数据"]
  E --> F["自动匹配；歧义项人工确认"]
  F --> G["生成有证据边界的复盘"]
  G --> H["团长确认私有创作记忆"]
  H --> I["用本次复盘生成下一条"]
  I --> B
```

验收重点不是“系统内部已经使用了记忆”，而是用户能明确看到：

- 本次复盘是否已确认；
- 形成的是哪一个记忆版本；
- 下一条内容是否使用了该版本；
- 下一轮只准备验证什么变化。

## 四、分批实施方案

### 第一批：对调试 API 实施环境硬隔离（P0）

#### 4.1 处理原则

正式团长端和运营端均已使用 `/api/app/*` 与 `/api/platform/*`。旧的 `/api/prototype/[...segments]` 用于本地原型调试和 CI 自动化测试，可以保留，但必须从“所有环境默认可用”改为“仅明确授权的非生产环境可用”。

环境隔离不能只依赖 `NODE_ENV`。当前 E2E 使用 `next start`，运行形态可能也是 production build，因此增加独立的应用环境标识和显式能力开关：

```text
APP_ENV=development | e2e | staging | production
ENABLE_PROTOTYPE_API=false
ALLOW_LIVE_MODEL=false
```

四类环境边界：

| 环境 | 调试 API | 数据库 | 模型 | 测试数据 |
| --- | --- | --- | --- | --- |
| 本地开发 | 可显式开启 | `.data/development.sqlite` | 默认 Fixture；显式允许后才可使用低额度开发 Key | 可使用 Demo |
| CI/E2E | 开启，仅监听 `127.0.0.1` | 每次运行独立的 `e2e-{pid}-{uuid}.sqlite` | 强制 Fixture | 自动创建、运行后废弃 |
| 共享测试 | 默认关闭；确需调试时使用测试令牌或正式登录权限 | 独立测试数据库 | 独立低额度测试 Key | 与生产数据完全分离 |
| 正式生产 | 固定关闭并返回 404 | `/srv/content-agent/data/production.sqlite` | 生产专用 Key | 禁止 Demo seed 和清理脚本 |

#### 4.2 代码调整

1. 增加集中式 `validateRuntimeEnvironment()`，在应用启动时校验环境组合。
2. 生产环境出现以下任意情况时拒绝启动：
   - `ENABLE_PROTOTYPE_API=true`；
   - `PROTOTYPE_TEST_MODE=true` 或 `PLAYWRIGHT_TEST_MODE=true`；
   - `PROTOTYPE_DEMO_CONTROLS=true` 或 `PROTOTYPE_ALLOW_DEMO_CLEAR=true`；
   - 未显式提供生产数据库绝对路径；
   - 生产数据库路径与测试、开发路径相同。
3. `/api/prototype/[...segments]` 在创建数据库连接、RunService 或模型客户端之前检查环境：未授权环境统一返回 404，且不得产生副作用。
4. 模型适配器改为：E2E 强制 Fixture；本地默认 Fixture；只有 `ALLOW_LIVE_MODEL=true` 时才使用开发模型 Key；生产正式接口使用生产 Key。
5. 生产环境禁止执行 `seed:demo`。正式首个账号通过受控初始化命令或管理员流程创建，不能依赖 Demo 数据。
6. Secure Cookie 由明确的公开访问环境决定，不能仅因两个测试开关被误开启就自动降级。
7. 增加路由安全回归测试：
   - 生产模式访问 `/api/prototype/*` 必须返回 404；
   - CI/E2E 模式显式开启后，调试接口可以访问并且只使用 Fixture；
   - 未登录访问 `/api/app/*` 必须返回 401；
   - 无权访问其他租户、IP、内容账号时返回 403 或 404；
   - 被拒绝的请求不得新增 Run、模型调用日志或 token 使用记录。
8. 日志只记录请求追踪号、用户、租户、动作和结果，不记录完整 Prompt、密钥或用户敏感内容。

#### 4.3 验收标准

- 生产环境中匿名 `POST /api/prototype/runs` 从 201 变为 404。
- 连续生产匿名请求不会初始化调试服务、调用模型或改变数据库。
- CI/E2E 仍能通过显式开关使用调试接口，且不会连接开发或生产数据库、不会消耗真实模型额度。
- 共享测试环境默认不能匿名访问调试接口。
- 正式登录链路不受影响。

### 第二批：修复 IP 建档后的状态一致性（P1）

#### 4.4 根因

IP 建档确认后，客户端在同一时刻执行 `router.push()` 和 `router.refresh()`。顶部当前 IP 来自服务端布局，正文来自新页面请求，两者可能拿到不同一轮缓存或渲染结果，导致“正文是新 IP、顶部仍无 IP”。

#### 4.5 首版修复

1. 确认接口成功后使用 `window.location.replace("/app/today")` 完整加载服务端上下文。
2. 确认接口返回已创建的 `ipId`、`displayName`、默认内容账号和当前选择状态；前端确认字段完整后再跳转。
3. 跳转失败或接口失败时保留当前建档内容，显示明确错误，不让用户重复填写。
4. 暂不引入全局客户端状态容器。IP 建档是低频动作，完整导航比额外状态架构更可靠。

#### 4.6 验收标准

- 建立“周姐”后，顶部当前 IP、页面标题、选题请求上下文都显示“周姐”。
- 刷新、关闭后重新登录，仍默认进入最后选择的当前 IP。
- 创建第二个 IP 后可以切换，切换不污染另一个 IP 的口播稿、数据和记忆。

### 第三批：补齐复盘记忆到下一轮创作（P1）

#### 4.7 持久化确认状态

扩展复盘详情返回值，增加：

```ts
confirmation: {
  status: "unconfirmed" | "confirmed"
  memoryId: string | null
  memoryVersion: number | null
  confirmedAt: string | null
  sourceReviewId: string
}
```

具体调整：

1. `ReviewMemoryRepository` 增加按 `source_review_id` 查询已确认记忆的方法。
2. 当前复盘查询同时返回真实确认状态，前端不再用本地 `useState(false)` 判断。
3. 确认接口返回实际创建或已存在的记忆对象，而不是用复盘版本冒充记忆版本。
4. 确认操作保持幂等：同一复盘、同一内容哈希重复提交只返回原记忆，不产生新版本。
5. `MemoryPreview` 增加错误捕获和 `role="alert"`，失败后保留编辑内容并允许重试。
6. 页面刷新后仍显示“已形成私有记忆 vN”和确认时间。

#### 4.8 一键开始下一轮

新增正式接口：

```http
POST /api/app/creation/next-round
Content-Type: application/json

{
  "sourceReviewId": "review_xxx",
  "expectedMemoryVersion": 3
}
```

服务端必须完成以下校验：

- 用户具有当前 IP 和内容账号访问权限；
- 来源复盘属于当前租户、IP、内容账号；
- 来源复盘已确认；
- `expectedMemoryVersion` 是当前有效记忆版本；
- 不接受其他账号或旧版本记忆的拼接请求。

成功后创建新的 Agent Run，并在 `creation_run_context` 中记录：

- `tenant_memory_version`：实际使用的记忆版本；
- `trigger_type`：`review_followup`；
- `source_review_id`：本次复盘 ID。

为此增加一条只增字段、不改旧数据的数据库迁移：

```sql
ALTER TABLE creation_run_context ADD COLUMN trigger_type TEXT NOT NULL DEFAULT 'manual';
ALTER TABLE creation_run_context ADD COLUMN source_review_id TEXT;
```

前端流程：

1. 记忆确认成功后显示主按钮“用本次复盘生成下一条”。
2. 点击后由服务端创建新 Run，完成后进入 `/app/today`。
3. 今日创作页显示“已依据复盘记忆 vN”，并提供“查看依据”折叠区。
4. 新选题仍是一个推荐方向，用户可直接生成口播稿或换选题，不恢复多方向、多文案并列选择。

#### 4.9 样本门槛文案

沿用现有规则，不改变算法：

- 0～2 条独立匹配发布：仅陈述事实；
- 3～4 条：可形成暂定判断，但不能写入长期记忆；
- 5 条及以上：允许确认私有创作记忆。

界面增加进度文案，例如：“当前 3/5 条，还需 2 条独立发布数据才能形成长期记忆。”这里的“独立发布”按去重后的发布作品计算，不按导入行数或快照数量计算。

#### 4.10 验收标准

- 确认后刷新，状态和记忆版本不丢失。
- 连续点击两次确认只产生一个记忆版本。
- 非授权角色不能确认记忆或创建下一轮。
- 从复盘页生成的新 Run，其 `source_review_id` 和 `tenant_memory_version` 可在数据库和审计日志中追溯。
- 下一轮模型输入包含已确认记忆，但不包含未确认复盘草稿。
- 首页明确显示该轮使用的复盘记忆版本。

### 第四批：清理双轨代码与优化复盘页（P1/P2）

#### 4.11 可直接删除的旧表层

在完成引用检查并通过测试后删除：

- `src/components/PrototypeWorkspace.tsx`；
- `src/components/SimulationAndReview.tsx`；
- `src/lib/api-client.ts`；
- 只验证上述旧界面的单元测试；
- 已无正式调用方的 `MetricsReviewService` 及其测试。

#### 4.12 不能直接删除的核心能力

正式创作链路仍复用了部分早期命名的领域服务、Run 状态机、仓储和 LLM 适配器。它们应先保留，后续仅做命名和目录重构，不能因文件名带有 `prototype` 或历史痕迹就整体删除。

清理顺序必须是：确认正式引用 → 删除旧入口 → 执行全量测试 → 再决定是否重命名核心模块。

#### 4.13 复盘页信息层级

不改变业务能力，只调整呈现：

1. 首屏显示：本轮结论、样本可信度、记忆状态和下一步动作。
2. 未匹配、歧义匹配和导入错误始终展开并置顶。
3. 已成功匹配的明细默认折叠，显示数量摘要。
4. 证据边界紧邻结论，避免用户把推测理解为事实。
5. 导入、匹配、复盘、记忆四个状态保持在同一条流程线上，可返回上一步修正。

## 五、接口与数据兼容策略

1. 数据库迁移只新增可空字段或带默认值字段，不修改现有表含义，不需要停机重建数据。
2. 旧 Run 的 `trigger_type` 自动视为 `manual`，`source_review_id` 为空，不影响读取。
3. 先部署兼容新旧数据的代码，再执行迁移；失败时可回滚应用版本，新字段保留不会影响旧代码。
4. 调试 HTTP 入口不属于外部 API 合同；生产环境固定关闭，因此不提供生产兼容期。开发和 CI 的调用方式通过显式环境开关继续保留。
5. 发布前备份 SQLite 数据库文件，并验证备份可打开、关键表行数一致。

## 六、测试计划

### 6.1 单元测试

- 记忆确认状态映射、真实版本返回和错误显示；
- 确认幂等、过期复盘冲突、内容哈希冲突；
- 下一轮创建的租户/IP/账号/记忆版本校验；
- 创建血缘中的 `trigger_type` 和 `source_review_id`；
- 0～2、3～4、5 条以上样本门槛文案与权限。

### 6.2 接口集成测试

- 所有正式 API 的未登录、越权和跨租户访问；
- 生产模式下旧 `/api/prototype/*` 固定返回 404，E2E 模式显式开启后只使用隔离数据库和 Fixture；
- 确认记忆后 GET 当前复盘返回持久化状态；
- `next-round` 只接受当前已确认记忆；
- 被拒绝请求不产生模型调用和数据库副作用。

### 6.3 端到端测试

新增一条完整闭环场景：

1. 登录；
2. 新建 IP 并验证顶部名称；
3. 生成选题和口播稿；
4. 分段编辑、定稿、下载；
5. 登记发布；
6. 导入真实数据并处理歧义匹配；
7. 生成复盘；
8. 确认私有记忆；
9. 刷新确认状态仍存在；
10. 点击“用本次复盘生成下一条”；
11. 验证新 Run 使用正确记忆版本和来源复盘。

## 七、开发顺序与提交拆分

| 批次 | 独立提交 | 预计工作量 | 是否阻断上线 |
| --- | --- | ---: | --- |
| 1 | 对调试 API 实施环境硬隔离、启动校验和安全回归测试 | 0.5～1 人日 | 是 |
| 2 | 修复 IP 建档后的服务端上下文刷新 | 0.5 人日 | 是 |
| 3A | 记忆确认状态持久化、幂等和错误处理 | 0.5～1 人日 | 是 |
| 3B | 复盘一键生成下一轮及血缘迁移 | 1 人日 | 是 |
| 4 | 删除旧表层、优化复盘页信息层级 | 0.5～1 人日 | 否，但建议首版完成 |

总计约 **3～4 人日**，包含自动化测试和一次完整人工验收；不包含真实平台 API 接入和产品侧内容质量门禁。

建议每个批次独立提交，避免把安全修复、数据库迁移和 UI 调整混在一个提交里。第一至第三批完成并通过完整闭环测试后，才满足首版生产交付条件。

## 八、上线与回滚

### 上线前

- 保存当前应用版本号和 Git 提交；
- 备份 SQLite 数据库；
- 在与生产相同环境执行迁移和完整闭环；
- 检查模型配置、文件上传目录权限和磁盘余量；
- 确认 `APP_ENV=production`，数据库使用生产绝对路径；
- 确认生产环境未开启调试 API、测试、Demo、模拟或清理开关；
- 确认生产、共享测试和开发使用不同数据库与不同模型 API Key。

### 上线后快速验证

- 匿名访问旧 API 返回 404；
- 团长登录、IP 切换、今日创作正常；
- 运营端爆款结构库权限不对团长开放；
- 数据导入、人工匹配、复盘确认和下一轮创建正常；
- 模型错误有可读提示，且不会重复扣费式重试。

### 回滚

- 应用异常：回滚到上一 Git 版本；
- 新增字段无需删除，旧代码会忽略；
- 若出现数据写入异常，停止写入后恢复上线前数据库备份；
- 不使用破坏性降级迁移，不在回滚时删除新字段或历史记忆。

## 九、明确不纳入本次修复
