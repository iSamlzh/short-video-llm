# IP 建档问题库与内容画像详细设计

日期：2026-08-18

状态：待用户书面复核

适用范围：第一版内容闭环中的首次 IP 建档与新增 IP

## 1. 设计结论

IP 建档不再依赖“IP 名称 + 一段自由介绍”直接生成画像，改为：

```text
基础信息
  -> 用户选择行业类目
  -> 从该行业至少 30 道受控问题中确定性选择 7 至 10 道
  -> 用户逐题回答
  -> 用户检查回答摘要
  -> 一次模型调用生成内容画像
  -> 用户核对画像及回答依据
  -> 原子确认 IP v1 与首个账号
  -> 进入今日创作并生成第一条口播稿
```

问题不是为了建立传统客户档案，而是为了给选题方向和口播稿提供可追溯的内容依据。每道题都必须映射到至少一个画像字段和一个选题输入字段。没有明确用途的问题不得进入正式问题库。

## 2. 已确认产品决策

1. 行业由用户主动选择，Agent 不推荐、不猜测行业。
2. 首版提供十个行业类目：
   - 健康养生
   - 美容护肤
   - 母婴育儿
   - 食品生鲜
   - 家居日用
   - 服饰穿搭
   - 本地生活与实体门店
   - 教育培训与知识服务
   - 创业经营与商业服务
   - 其他
3. 每个行业必须拥有不少于 30 道已启用问题。
4. 每次新建 IP 只选择 7 至 10 道问题；信息覆盖充分时可以提前结束，但不得少于 7 道。
5. 问题选择采用平台确定性规则，不随机抽取，不调用模型，也不允许模型临时创造问题。
6. 建档过程不调用模型；用户确认回答摘要后，画像生成只调用模型一次。
7. 问题和回答围绕内容产出，直接支持受众、用户问题、观点、素材、表达、产品连接、行动引导、边界和长期选题方向。
8. 用户可返回修改答案；修改后生成新的待确认画像版本，不直接覆盖已确认 IP。
9. 已有 IP 数据继续可用，新字段保持向后兼容。

## 3. 目标与非目标

### 3.1 目标

- 用不超过 10 道问题获得足以支持首轮选题的结构化画像。
- 让每个画像结论、选题依据和后续文案事实可以追溯到用户原始回答。
- 降低模型凭空补全经历、受众和产品信息的概率。
- 让不同行业获得不同的问题表达和内容信号，而不是使用同一套简历式表单。
- 问题库可版本化、可测试、可扩展，并能在未来进入平台运营治理流程。

### 3.2 非目标

- 第一版不建设问题库运营后台。
- 第一版不由模型生成新问题或调整问题文案。
- 第一版不进行医疗、法律或产品资质自动判断。
- 第一版不要求用户填写专业批准文号、证据等级等高门槛资料。
- 第一版不因问题库更新自动改写已确认 IP。

## 4. 内容画像模型

### 4.1 画像维度

| 画像维度 | 要回答的内容问题 | 直接影响的选题判断 |
|---|---|---|
| IP 身份与可信来源 | 为什么由这个人来讲 | 可信叙事视角、可使用事实 |
| 目标受众 | 希望谁刷到内容 | 受众范围、称呼和情境 |
| 用户问题库 | 用户经常为什么困扰或咨询 | 选题母题、冲突和痛点 |
| 核心观点库 | IP 坚持什么判断 | 观点型选题和差异化表达 |
| 真实素材库 | 有什么经历、过程和日常可讲 | 故事、案例、现场与证据 |
| 表达方式 | 更习惯怎样讲 | 口播结构、开头和语言风格 |
| 产品或服务连接 | 如何自然进入内容 | 产品出现位置和商业边界 |
| 行动引导 | 希望观众看完做什么 | CTA 类型和强度 |
| 表达边界 | 哪些话和内容不能使用 | 发布前硬性质量门槛 |
| 长期选题方向 | 哪些主题可以持续讲 | 今日选题候选范围和权重 |

### 4.2 结构化画像

```ts
type ContentPortrait = {
  schemaVersion: number
  questionSetVersion: string
  industryCategory: string
  identityPositioning: string
  credibilitySources: string[]
  targetAudience: string
  audienceQuestions: string[]
  coreBeliefs: string[]
  contentAssets: string[]
  presentationStyles: string[]
  commercialConnections: string[]
  desiredActions: string[]
  boundaries: string[]
  topicPillars: Array<{
    title: string
    rationale: string
    sourceQuestionIds: string[]
  }>
  confirmedFacts: Array<{
    statement: string
    sourceQuestionIds: string[]
  }>
  uncertainties: Array<{
    statement: string
    relatedQuestionIds: string[]
  }>
  sourceMap: Record<string, string[]>
}
```

`sourceMap` 的键为画像字段路径，值为提供依据的问题编号。选题 Agent 获得画像内容、来源问题及置信状态，不只获得一段人物简介。

### 4.3 存量字段兼容

继续生成并保存下列字段，作为现有创作服务的兼容投影：

```ts
type LegacyIpProfile = {
  displayName: string
  experience: string
  expertise: string
  audience: string
  voiceStyle: string
  boundaries: string
}
```

新画像通过单独的投影函数生成旧字段，不在 UI 或 LLM 调用处重复拼装。存量 IP 没有 `contentPortrait` 时继续使用旧字段；新 IP 优先读取结构化画像。

## 5. 行业问题库

### 5.1 问题定义

```ts
type PortraitQuestion = {
  id: string
  baseTemplateId?: string
  industryCategory: string
  questionSetVersion: string
  dimension: PortraitDimension
  prompt: string
  helpText?: string
  answerType: "single_choice" | "multi_choice" | "short_text" | "long_text"
  options?: Array<{ value: string; label: string; signals: string[] }>
  requiredAnchor: boolean
  canAnswerNone: boolean
  priority: number
  trigger: QuestionTrigger
  outputFields: string[]
  topicSignals: string[]
  status: "draft" | "active" | "retired"
}
```

### 5.2 数量和覆盖约束

每个行业问题包必须同时满足：

- 已启用问题不少于 30 道。
- 十个画像维度均有问题覆盖。
- 受众、用户问题、真实素材和内容目标四个核心维度各至少 3 道候选问题。
- 不得出现两个含义相同、只替换少量词汇的重复问题。
- 至少 60% 的问题使用行业真实语境，不使用泛化简历措辞。
- 每道题至少配置一个 `outputFields` 和一个 `topicSignals`。
- 问题文案只询问一个认知任务，不把多个问题合并在一个句子中。

不同问题可以引用同一个 `baseTemplateId` 复用校验和信号规则，但每个行业仍拥有独立的问题编号、行业文案和启用状态。

### 5.3 内容写作标准

合格问题必须让回答直接改变至少一种内容决策，例如：

- 选题面向谁；
- 从什么场景切入；
- 使用哪类真实素材；
- 采用观点、故事、问答、避坑还是现场结构；
- 产品在内容中如何出现；
- 观众看完应执行什么动作；
- 哪些事实和表达不得进入文案。

“你的职位是什么”“你的年龄是多少”等不能直接改变内容判断的问题，除非该行业的选题确实依赖该信息，否则不进入问题库。

## 6. 确定性问题选择器

### 6.1 选择目标

从当前行业的至少 30 道问题中选出 7 至 10 道，使画像维度覆盖充分、问题不重复、顺序自然，并保证相同输入和问题库版本得到相同结果。

### 6.2 选择阶段

1. 选择四道核心锚点题，分别覆盖目标受众、用户问题、真实素材和内容目标。
2. 根据锚点题中的结构化信号计算未覆盖维度。
3. 对剩余候选题计算确定性得分：
   - 未覆盖维度优先；
   - 与用户已选信号匹配优先；
   - 行业问题优先于泛化问题；
   - 高优先级问题优先；
   - 与已回答问题语义或映射重复时排除。
4. 每次选择下一题时重新计算覆盖，但不修改已经回答的问题顺序。
5. 第 7 题回答后开始判断是否达到结束条件；最多选择到第 10 题。

### 6.3 结束条件

以下条件全部满足时可以结束：

- 已回答至少 7 题；
- 四个核心维度全部覆盖；
- 至少覆盖 8 个画像维度；
- 受众、用户问题、真实素材和边界都有非空信号；
- 没有仍处于阻断状态的条件问题。

### 6.4 禁止行为

- 禁止 `Math.random()` 或其他随机选择。
- 禁止在建档中调用模型决定下一题。
- 禁止选择问题库之外的问题。
- 禁止只按优先级取前 10 题而忽略画像覆盖。
- 禁止因问题库版本更新改变进行中的建档会话。

## 7. 建档状态与持久化

### 7.1 状态机

```text
BASIC_INFO
  -> INDUSTRY_SELECTED
  -> ANSWERING
  -> REVIEWING_ANSWERS
  -> GENERATING_PORTRAIT
  -> PORTRAIT_PREVIEW
  -> CONFIRMED
```

异常状态为 `GENERATION_FAILED` 和 `EXPIRED`。失败只记录本次画像生成，不丢弃答案。

### 7.2 数据库存储

第一版新增单一会话表 `ip_onboarding_sessions`：

| 字段 | 用途 |
|---|---|
| `id` | 建档会话编号 |
| `tenant_id` | 租户隔离 |
| `creator_user_id` | 创建人 |
| `display_name` | IP 名称 |
| `primary_platform` | 首个内容平台 |
| `industry_category` | 用户选择的行业 |
| `question_set_version` | 冻结的问题库版本 |
| `state` | 当前状态 |
| `answers_json` | 原始回答及问题版本 |
| `selection_trace_json` | 每道题被选中的规则依据 |
| `portrait_draft_json` | 当前待确认画像 |
| `portrait_draft_version` | 待确认画像版本 |
| `created_at` / `updated_at` | 生命周期时间 |
| `confirmed_at` | 正式确认时间 |

会话在服务端按题保存，刷新、换设备或模型失败后均可恢复。用户确认后，在同一事务中创建 `ip_profiles`、首个 `content_accounts`、成员范围和当前上下文；会话状态变为 `CONFIRMED`。

## 8. 服务与接口

### 8.1 模块职责

| 模块 | 唯一职责 |
|---|---|
| `ip-question-bank` | 加载、验证和按版本冻结行业问题库 |
| `ip-question-selector` | 根据覆盖和信号确定下一题 |
| `ip-onboarding-session-service` | 管理会话、答案、状态和恢复 |
| `ip-portrait-service` | 一次模型调用生成结构化画像 |
| `ip-profile-service` | 原子确认 IP、账号、范围和当前上下文 |
| `ip-profile-projector` | 在新画像和旧字段之间进行兼容投影 |

各模块通过类型化对象通信。页面组件不得直接读取问题库文件或拼装数据库 JSON。

### 8.2 接口建议

| 方法与路径 | 用途 |
|---|---|
| `POST /api/app/ip-onboarding/sessions` | 创建会话并冻结行业与问题库版本 |
| `GET /api/app/ip-onboarding/sessions/:id` | 恢复当前会话和下一题 |
| `PUT /api/app/ip-onboarding/sessions/:id/answers/:questionId` | 保存或修改单题答案 |
| `POST /api/app/ip-onboarding/sessions/:id/review` | 校验覆盖并返回回答摘要 |
| `POST /api/app/ip-onboarding/sessions/:id/portrait-preview` | 一次模型调用生成待确认画像 |
| `POST /api/app/ip-onboarding/sessions/:id/confirm` | 原子创建并选择 IP v1 |

写接口支持幂等键或版本号。过期版本写入返回 `409 VERSION_CONFLICT`，前端恢复服务端最新状态，不覆盖用户较新的答案。

## 9. 模型输入与输出

画像模型只接收：

- 用户明确填写的 IP 名称；
- 用户选择的行业和主要平台；
- 问题编号、问题文案、问题维度和原始回答；
- 需要生成的类型化 Schema；
- 不得虚构、不得把未确认内容写成事实的规则。

模型不得：

- 修改用户选择的行业；
- 创造用户没有提供的经历、案例、数据或产品效果；
- 把“暂时没有”补全为看似完整的事实；
- 生成问题库之外的补充访谈；
- 输出没有 `sourceQuestionIds` 的长期选题方向或已确认事实。

服务端用 Zod 校验模型输出。结构校验失败时允许一次受控修复重试；仍失败则返回可恢复错误并保留答案。

## 10. 用户界面

### 10.1 页面路径

1. 基础信息：IP 名称和主要平台。
2. 行业选择：十个行业单选，`其他` 允许填写具体行业名称。
3. 逐题问答：每屏一个认知任务，选择题支持“自己填写”。
4. 回答摘要：按内容依据维度分组，不使用长表格。
5. 画像生成：说明正在整理受众、问题、素材和选题方向，不显示虚假百分比。
6. 画像确认：显示结构化画像、原始依据和仍不确定的信息。

### 10.2 交互规则

- 顶部显示“已获得 N 项内容依据”，不使用僵硬的固定十步进度条。
- 用户可以查看全部回答、返回修改和继续建档。
- 必答锚点题不可跳过；补充题允许选择“暂时没有”。
- 回答保存成功后才进入下一题；保存失败保留当前输入并支持重试。
- 用户纠正画像时必须有明确的“提交纠正并重新生成”动作。
- 只有用户执行“这个理解准确，开始创作”后才建立当前 IP。
- 日常登录直接使用当前 IP，不重复建档；只有新增 IP 时重新进入该流程。

### 10.3 响应式与可访问性

- 桌面和移动端均保持单列主任务，不建设侧边栏和卡片仪表盘。
- 问题标题、帮助说明、输入控件、错误和主动作具有明确阅读顺序。
- 选择项使用原生可访问语义；键盘可以完成选择、返回和提交。
- 焦点在切换题目后移动到新题标题；异步保存和生成状态使用可感知状态播报。
- 文本、边框、错误和焦点状态满足 WCAG AA 对比度要求。

## 11. 异常与降级

| 场景 | 系统行为 |
|---|---|
| 页面刷新或换设备 | 从服务端会话恢复已答问题和下一题 |
| 单题答案保存失败 | 保留本地输入，提示重试，不前进 |
| 问题库缺少当前版本 | 阻止创建新会话；进行中会话读取随发布保留的版本包 |
| 行业问题包校验失败 | 发布阶段阻断；运行时不得静默换成未审问题 |
| 画像模型超时 | 保留答案，进入 `GENERATION_FAILED`，允许幂等重试 |
| 模型结构不完整 | 一次受控修复重试；失败后不保存残缺画像 |
| 用户修改已答问题 | 使当前画像草稿失效，重新进入回答检查 |
| 确认事务失败 | IP、账号、范围和当前上下文全部回滚 |

“通用问题兜底”只能作为正式发布的问题库版本存在，不能在运行时绕过版本治理临时拼接问题。

## 12. 性能与成本

- 逐题选择和答案保存不调用模型。
- 问题库在应用启动后按版本缓存，选择器只处理当前行业的候选集合。
- 画像生成每个新 IP 默认一次模型调用，结构修复最多增加一次调用。
- 会话和画像创建均为低频操作，不改变今日创作的并发模型。
- 首版继续适配单台 4 核 8GB 部署，不引入独立队列或新基础设施。

## 13. 测试策略

### 13.1 问题库静态检查

- 十个行业均存在。
- 每个行业已启用问题不少于 30 道。
- 问题编号在全库唯一。
- 十个画像维度完整覆盖。
- 每题均配置画像映射和选题信号。
- 问题版本、选项、触发条件和状态满足 Schema。

### 13.2 选择器单元测试

- 任意行业结果不少于 7 道、不超过 10 道。
- 四个核心锚点维度一定出现。
- 相同输入和版本得到相同问题顺序。
- 已覆盖维度不会被同义问题重复追问。
- 条件题只在触发条件满足时出现。
- 第 10 题后强制结束并进入覆盖校验。

### 13.3 服务和接口测试

- 租户、用户和会话范围隔离。
- 单题保存、重复提交和版本冲突。
- 刷新恢复、答案修改和画像失效。
- 模型超时、结构错误和幂等重试。
- 确认事务成功与完整回滚。
- 新画像向旧字段的兼容投影。

### 13.4 页面与端到端测试

- 首次登录进入建档；已有当前 IP 直接进入今日创作。
- 选择行业、逐题回答、查看摘要、返回修改。
- 生成画像、查看依据、提交纠正、确认画像。
- 确认后创建当前 IP 并自动生成第一条口播稿。
- 桌面和移动端完成完整任务；键盘操作和状态播报可用。

## 14. 验收标准

1. 十个行业问题包通过自动静态检查，每个行业至少 30 道已启用问题。
2. 任一新 IP 实际回答 7 至 10 道题，并满足核心画像维度覆盖。
3. 所有问题可追溯到画像字段和选题输入，不存在无用途问题。
4. 建档问答阶段不产生模型请求；画像生成默认只产生一次模型请求。
5. 画像中的长期选题方向和已确认事实均带来源问题编号。
6. 刷新、换设备、模型失败和单题保存失败后能够继续流程。
7. 用户修改答案后不会静默覆盖已确认画像。
8. 存量 IP 无需迁移即可继续生成选题和口播稿。
9. 确认画像后直接进入今日创作，并以新画像生成第一条口播稿。
10. 问题库、选择器、服务、接口和页面均有自动化测试。

## 15. 发布与兼容策略

1. 先交付问题库 Schema、静态检查和十个行业问题包。
2. 再交付选择器和建档会话持久化。
3. 接入画像模型、兼容投影和确认事务。
4. 最后替换现有两字段建档页面并完成端到端验证。
5. 新流程只应用于新建 IP；存量 IP 保持原数据和当前上下文。
6. 问题库随系统基线包版本发布，进行中的会话始终固定使用创建时的版本。
